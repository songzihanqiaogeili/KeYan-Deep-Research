# 科研 Agent：源码学习与面试演示

这份路线围绕本项目实际实现，配合修改后的黑马点评讲工程能力。先跑懂一条完整任务，再逐层解释，不需要背完整仓库。

## 核心定位与实现边界

以问题或种子论文为入口，从学术索引发现文献，定向阅读并整理可定位证据，输出方法对照和阅读路线。LangGraph 管主流程，模型在有限位置决策；不是每个函数都自主行动。当前单用户本机工作台，SQLite 队列/缓存/阶段工件；不是多租户分布式生产集群。

## 源码模块地图

以下路径均位于 backend/app/scientific_research：

| 模块 | 优先阅读 | 必须能解释 |
|---|---|---|
| 主流程 | pipeline.py、runner.py | 7阶段如何衔接，阶段工件在哪里，哪些可重用，失败走哪里 |
| 上下文 | policy.py、context_engine.py、context_builder.py | 不同角色为何看到不同字段；原文/引文不静默截断；字符不是token |
| 记忆 | research_memory.py、store.py | 工作状态、缓存、历史线索的区别；何时写入/召回/失效/删除 |
| 工具与循环 | agent_loop.py、providers.py、literature.py | 可用工具如何随状态变化；参数如何验证；重复动作、无进展、步数和调用预算如何限制 |
| 文献发现 | trend.py、seed_search.py、requirements.py | 问题查询优先、方法查询补充、元数据条件不等于论文质量 |
| RAG | rag.py、embeddings.py、retrieval.py | BM25/向量各负责什么，RRF融合，片段与论文级检索区别，故障回退 |
| 证据与报告 | evidence.py、workflow.py、branch_report.py、reporting.py、report_diagnostics.py | 引文定位与语义支持区别；审核器是否看到被引用原文；哪些诊断可以程序确定 |
| 观测 | observability.py、tracing.py | 模型实际usage、缺失用量、失败调用、嵌入成本、父子span、脱敏 |
| 接口 | webapp.py、mcp_server.py | 本机令牌、跨站限制、论文权限边界；外部只读MCP与内部工具不是同一回事 |

## 第一层：要能独立讲和改

1. 一张图解释输入→检索→索引→阅读分析→写作→审核→交付。指出哪些是普通程序步骤，哪些是LLM决策。
2. 追踪一次 controller 的 JSON action，经程序校验、工具执行、观察结果、再次决策。当前是结构化 JSON 决策+本地分发，不冒充模型厂商原生 function calling。
3. 解释 role 白名单与调用边界预算。来源文本可含提示注入，不能成为系统指令、工具权限或配置。
4. 区分任务内原文RAG、论文候选语义排序和外部索引发现；没有入库的论文向量检索无法凭空找到。
5. 解释失败如何恢复：从入口重调度，复用工件；当前不是 LangGraph 原生 checkpointer 的任意节点自动续跑，也不承诺模型请求恰好一次。
6. 能现场改一个工具限额或上下文字段，先写失败回归，再证明行为变化。

掌握标准不是背术语：关掉嵌入服务、给一个无权限动作、换一篇种子论文，能根据代码预测结果并验证。

## 第二层：工程追问

- 并发：为什么用 Semaphore；每篇reader局部产物何时归并；一个失败是否丢其他结果；取消如何传播。
- 缓存：键包含文档、研究条件、模型、Skill与实际检索身份；为什么向量故障不能污染健康缓存；为何并发reader要冻结自己选片段时的身份。
- 预算：累计生成调用恢复不清零，检索/嵌入请求有总时限和独立上限；模型未返回usage时不能当0token。
- 记忆：保存源记录和检索线索，不保存模型推断当事实；新任务重新检索核验；恢复固定快照；删除记忆不删除研究历史。
- 数据：摘要不足以验证全文实验；索引日期不等于正式发表日期；顶刊名单需有年份/来源，不能靠模型口述。
- 输出：审核有界，程序先查引用/排除约束/重复文本，语义是否成立仍需核验；资料不足允许部分交付。

## 五分钟面试叙述

“我做了一个科研文献探索 Agent，支持问题和论文两种入口。早期把搜到的摘要拼成长报告，相关性和论证质量都不稳定，所以我把发现、取证、对照、写作分开，建立证据可定位的数据契约。用LangGraph编排任务，保留一个有预算的工具选择循环。RAG用于本次材料取证和已召回候选排序，跨任务记忆只作为新检索线索。工程上处理限流、失败隔离、恢复、缓存身份和用量观测。现在功能回归和本机模型试跑已做，正式科学报告质量评测还未完成，不能宣称已经达到专业综述质量。”

把其中每句对应到一段代码、一个失败案例和一条验证记录；不要直接背这段话。

## 建议演示顺序

- 准备一条真实研究记录，显示检索查询、筛选原因、报告和原文引用。
- 展开“完整工作流与运行诊断”，说明某阶段的耗时和实际用量。
- 展示一个控制好的失败：来源离线、嵌入关闭或无效工具。用合成夹具演示时明确说明，不把夹具伪装成真实效果。
- 展示恢复后调用次数不重置、成功工件复用，再打开相关回归测试。
- 最后指出一个仍未解决的问题，例如语义审核、开放获取全文覆盖或评价集。

## 与修改后的黑马点评组合

Agent项目展示LLM系统工程：上下文、工具、循环、RAG、记忆、观测与失败处理。黑马点评展示你实际完成的后端工程：接口、数据库、Redis、事务/并发和测试。具体亮点必须以你的代码为准，本轮没有读取或修改黑马点评，不能假定你做过秒杀优化、消息队列或分布式锁改造。

每个项目准备“原问题→你的设计→为何不用另一个方案→失败案例→验证结果”五句话。简历只写确实实现的技术，不写Milvus全局论文库、分布式调度、原生function calling或原生checkpointer恢复，除非后续真正补齐。

## 暂缓内容

不急着堆更多Agent、换大规模向量库或增加自动代码执行。正式评测后续用固定研究题、人工标注相关论文和证据支持情况，分别测召回、选文、引用与报告；当前结构诊断与单元测试不能替代这些指标。
